# Архитектурное решение по логированию

## Мотивация

### Текущая проблема
Разбор инцидентов происходит "со слов клиента":
- Нет централизованного источника правды о том, что произошло
- Разработчики тратят часы на поиск проблемы без логов
- Невозможно понять, где именно потерялся заказ
- Поддержка перегружена ручным разбором каждого случая

### Что даст логирование бизнесу

**Финансовый эффект:**
- Снижение потерь от простоя (быстрое обнаружение проблем)
- Уменьшение затрат на поддержку (self-service для support team)
- Предотвращение loss of revenue (раннее обнаружение аномалий)

**Операционный эффект:**
- Быстрый разбор инцидентов (от часов к минутам)
- Проактивное обнаружение проблем (до жалоб клиентов)
- Compliance и audit trail для регуляторов

### Влияние на метрики

| Метрика | До логирования | После логирования | Улучшение |
|---------|----------------|-------------------|-----------|
| **MTTR** (Mean Time To Resolution) | 4-8 часов | 15-30 минут | **16x** |
| **Support ticket resolution time** | 2-3 дня | 2-4 часа | **12x** |
| **Customer Satisfaction (CSAT)** | 60% | 85%+ | +25 пп |
| **Proactive incident detection** | 0% (reactive) | 70%+ | - |
| **Revenue loss from undetected issues** | ~$5k/месяц (estimate) | <$500/месяц | **10x** |

**Технические метрики:**
- Error detection rate: 100% (vs текущие ~20% через жалобы)
- Time to detect anomaly: <5 минут (vs часы/дни)

## Какие логи собирать

### Уровни логирования

- **INFO**: бизнес-события, успешные операции
- **WARN**: потенциальные проблемы, slow queries
- **ERROR**: ошибки, exceptions, 5xx
- **DEBUG**: только dev/staging

### Логи по системам

#### Shop API (Java Spring Boot)

| Событие | Уровень | Обязательные поля | Пример |
|---------|---------|-------------------|--------|
| Order created | INFO | `order_id`, `customer_id`, `timestamp`, `items_count`, `total_amount` | `{"level":"INFO","event":"order.created","order_id":"ORD-12345","customer_id":"CUST-567","items":3}` |
| Order submitted | INFO | `order_id`, `status_from`, `status_to`, `timestamp` | `{"event":"order.status_changed","order_id":"ORD-12345","from":"INITIATED","to":"SUBMITTED"}` |
| File uploaded | INFO | `order_id`, `file_size`, `file_format`, `s3_key` | `{"event":"file.uploaded","order_id":"ORD-12345","size_mb":5.2,"format":"STL"}` |
| HTTP request | INFO | `method`, `url`, `status_code`, `duration_ms`, `user_id` | `{"method":"POST","url":"/api/orders","status":201,"duration":145}` |
| RabbitMQ publish | INFO | `exchange`, `routing_key`, `message_id`, `order_id` | `{"event":"rabbitmq.publish","exchange":"order_events","key":"order.submitted","order_id":"ORD-12345"}` |
| Slow query | WARN | `query`, `duration_ms`, `table` | `{"level":"WARN","event":"slow_query","duration":1500,"table":"orders"}` |
| Exception | ERROR | `exception_type`, `message`, `stack_trace`, `order_id` (if available) | `{"level":"ERROR","exception":"SQLException","message":"Connection timeout","stack":"..."}` |

#### MES API (C#)

| Событие | Уровень | Обязательные поля |
|---------|---------|-------------------|
| Price calculation started | INFO | `order_id`, `file_polygons`, `complexity`, `timestamp` |
| Price calculation completed | INFO | `order_id`, `price`, `duration_ms`, `complexity` |
| Order assigned to operator | INFO | `order_id`, `operator_id`, `timestamp` |
| Manufacturing started/completed | INFO | `order_id`, `operator_id`, `status`, `timestamp` |
| Dashboard loaded | INFO | `user_id`, `filters`, `duration_ms`, `orders_count` |
| S3 download | INFO | `order_id`, `s3_key`, `duration_ms`, `size_mb` |
| RabbitMQ consume | INFO | `queue`, `message_id`, `order_id` |
| Slow dashboard query | WARN | `duration_ms`, `filters`, `result_count` |
| Price calculation timeout | ERROR | `order_id`, `duration_ms`, `reason` |

#### CRM API (Java Spring Boot)

| Событие | Уровень | Обязательные поля |
|---------|---------|-------------------|
| Order approval | INFO | `order_id`, `seller_id`, `approved`, `timestamp` |
| Status update | INFO | `order_id`, `status_from`, `status_to`, `seller_id` |
| RabbitMQ event | INFO | `queue`, `event_type`, `order_id` |
| Failed approval | WARN | `order_id`, `seller_id`, `reason` |
| Exception | ERROR | `exception_type`, `message`, `stack_trace` |

#### RabbitMQ

| Событие | Уровень | Обязательные поля |
|---------|---------|-------------------|
| Message published | INFO | `exchange`, `routing_key`, `message_id`, `size_bytes` |
| Message consumed | INFO | `queue`, `message_id`, `consumer_tag` |
| Message moved to DLQ | ERROR | `queue`, `message_id`, `reason`, `retry_count` |
| Queue size threshold | WARN | `queue`, `size`, `threshold` |
| Connection lost | ERROR | `service`, `reconnect_attempt` |

#### Инфраструктура

| Событие | Уровень | Обязательные поля |
|---------|---------|-------------------|
| Application startup | INFO | `service`, `version`, `environment` |
| Health check failed | WARN | `service`, `check_type`, `reason` |
| Resource exhaustion | ERROR | `service`, `resource_type` (CPU/Memory), `value` |

### Формат логов (Structured JSON)

```json
{
  "timestamp": "2026-01-31T14:50:23.123Z",
  "level": "INFO",
  "service": "shop-api",
  "environment": "production",
  "event": "order.created",
  "trace_id": "abc123def456",  // correlation with traces
  "span_id": "789ghi",
  "order_id": "ORD-12345",
  "customer_id": "CUST-567",
  "items_count": 3,
  "total_amount": 15000,
  "message": "Order created successfully"
}
```

**Ключевые поля:**
- `trace_id` - связь с distributed tracing (Jaeger)
- `service` - откуда лог
- `event` - категория события (для группировки)
- `timestamp` - ISO 8601 с timezone

## Приоритизация: что логировать первым

### Приоритет 1 (немедленно, спринт 1-2)

**1. MES API** (2 недели)
- **Почему первым:** Здесь теряются заказы (расчёт цены, обработка очередей)
- **Критичные логи:**
  - Price calculation (start/end, duration, errors)
  - RabbitMQ consume (DLQ messages!)
  - Operator actions
  - S3 operations
- **Проблема:** Долгий расчёт (2-30 мин), но нет видимости, что происходит

**2. Shop API** (1.5 недели)
- **Почему вторым:** Точка входа для B2C и B2B клиентов
- **Критичные логи:**
  - Order lifecycle (created → submitted)
  - File uploads
  - RabbitMQ publish
  - HTTP requests (особенно 5xx)
- **Проблема:** Клиенты не получают заказы, но не понятно, отправился ли он в MES

**3. RabbitMQ** (1 неделя)
- **Почему третьим:** Интеграционный слой, где теряются сообщения
- **Критичные логи:**
  - DLQ messages (!!!!)
  - Queue sizes
  - Message routing
- **Проблема:** Сообщения теряются, но неизвестно где и почему

### Приоритет 2 (спринт 3-4)

**4. CRM API** (1 неделя)
- Менее критично, т.к. проблемы реже возникают здесь
- Но нужно для полной картины

**5. Инфраструктура** (ongoing)
- Application logs (startup, health)
- Database slow queries

### Обоснование порядка

**MES первым:**
- Больше всего жалоб на "заказы в работе месяцами"
- Самая сложная логика (3D обработка, очереди)
- Расчёт цены - чёрный ящик сейчас

**Shop вторым:**
- High traffic (B2C + B2B)
- Первая точка контакта клиента
- Критично для revenue

**RabbitMQ третьим:**
- Связующее звено между всеми системами
- DLQ - индикатор потерянных заказов

## Предлагаемое решение

### Технологический стек: ELK Stack

**Компоненты:**
- **Elasticsearch** - хранение и индексирование логов
- **Logstash** - сбор, трансформация, enrichment
- **Kibana** - визуализация, дашборды, алертинг
- **Filebeat** - легковесный shipper на каждом сервисе

**Почему ELK:**
- Full-text search (критично для debugging)
- Aggregations для аналитики
- Open-source с большим community
- Интеграция с Jaeger (trace_id в логах)

### Архитектура

│  Shop API   │──┐

│  MES API    │──┤    └──────────┘      └──────────────┘      └─────────────┘

                 │                            │                       │

### Компоненты

1. **Filebeat** на каждом сервисе
2. **Logstash cluster** (2 instances)
3. **Elasticsearch cluster** (3 nodes)
4. **Kibana** (1 instance)

### Deployment

- Elasticsearch: 3 nodes, 8GB RAM
- Logstash: 2 instances
- Kibana: 1 instance
- **Cost:** ~$420/месяц

### Изменения в приложениях

- Shop API & CRM API (Java): `logback-json-classic` + LogstashEncoder
- MES API (C#): `Serilog` с JSON formatter

## Безопасность

### Чувствительные данные

**НЕ логируем (NEVER):**
- ❌ Полные номера кредитных карт
- ❌ Пароли
- ❌ Полные API keys
- ❌ PII: email, phone, physical address
- ❌ Passport numbers, tax IDs

**Маскируем (частично):**
- API keys: `xyz1****` (первые 4 символа)
- Customer ID: hash или UUID (не email)
- IP addresses: последний октет → 0 (123.45.67.0)

**Логируем безопасно:**
- `order_id` (UUID, не содержит PII)
- `customer_id` (UUID)
- Агрегированные метрики (count, avg)

### Log Scrubbing (Logstash filter)

```ruby
filter {
  # Маскировка credit cards
  mutate {
    gsub => [
      "message", "\b\d{4}[\s-]?\d{4}[\s-]?\d{4}[\s-]?\d{4}\b", "****-****-****-****"
    ]
  }

  # Маскировка email
  mutate {
    gsub => [
      "message", "\b[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\.[A-Z|a-z]{2,}\b", "[EMAIL_REDACTED]"
    ]
  }

  # Удаление полей с паролями
  mutate {
    remove_field => ["password", "api_secret"]
  }
}
```

### Контроль доступа (RBAC)

**Роли в Kibana:**

| Роль | Доступ | Индексы | Действия |
|------|--------|---------|----------|
| **Support** | Read-only | `logs-shop-api-*`, `logs-crm-api-*` | View, Search |
| **Developer** | Read-only | All `logs-*` | View, Search, Export |
| **DevOps** | Read/Write | All `logs-*` | View, Search, Create alerts, Manage indices |
| **Security** | Full | All | View, Audit, Delete |
| **Admin** | Full | All | Everything |

**Реализация (Elasticsearch Security):**
```yaml
# elasticsearch.yml
xpack.security.enabled: true
xpack.security.authc.realms.native.native1.order: 0

# Create roles
PUT /_security/role/support
{
  "indices": [
    {
      "names": ["logs-shop-api-*", "logs-crm-api-*"],
      "privileges": ["read"]
    }
  ]
}
```

**Дополнительно:**
- **SSO integration** - Yandex IAM для single sign-on
- **Audit logging** - кто, когда, какие логи просматривал
- **IP whitelist** - доступ только из корпоративной VPN
- **MFA** - для admin ролей

### Encryption

- **In transit:** TLS 1.3 между всеми компонентами
- **At rest:** Elasticsearch encryption-at-rest (X-Pack)
- **Kibana:** HTTPS only

## Политика хранения

### Индексы

**Структура:**
- Отдельный индекс на сервис и день: `logs-{service}-{date}`
- Примеры:
  - `logs-shop-api-2026.01.31`
  - `logs-mes-api-2026.01.31`
  - `logs-crm-api-2026.01.31`

**Aliases для удобства:**
- `logs-all` → все индексы
- `logs-production` → только prod
- `logs-errors` → только ERROR уровень

### Retention Policy

| Уровень логов | Retention | Объём (estimate) | Обоснование |
|---------------|-----------|------------------|-------------|
| **ERROR** | 90 дней | ~500 MB/месяц | Compliance, анализ трендов |
| **WARN** | 30 дней | ~1 GB/месяц | Диагностика recurring issues |
| **INFO** | 14 дней | ~5 GB/месяц | Operational debugging |
| **DEBUG** | 7 дней (dev only) | ~10 GB/месяц | Детальная диагностика |

**Total (production):** ~6.5 GB/месяц

**Рост нагрузки:** +100 заказов/месяц = +5% логов/месяц
- Через 12 месяцев: ~11 GB/месяц
- Планируем инфраструктуру с запасом x3 = 500 GB storage

### Index Lifecycle Management (ILM)

**Hot tier (0-7 дней):**
- SSD storage
- Быстрый поиск
- Активные запросы от Support/Devs

**Warm tier (8-30 дней):**
- HDD storage (дешевле)
- Редкие запросы
- Только ERROR и WARN

**Cold tier (31-90 дней):**
- S3-like storage (Yandex Object Storage)
- Только ERROR
- Для compliance и audit

**Delete (>90 дней):**
- Автоматическое удаление
- Исключение: критичные ERROR → архив в S3 Glacier (1 год)


### Архивирование для Compliance

**Что архивируем:**
- Все ERROR логи
- Security-related события (failed logins, access control)
- Financial transactions (order payments)

**Куда:**
- Yandex Object Storage (S3-compatible)
- Glacier tier (копейки за GB)

**Retention:** 1 год (для налоговой, audits)

## Аналитика и алертинг

### Алертинг через Kibana Alerts

#### 1. Error Rate Spike

**Условие:**
```
count(level:ERROR) > 10 in last 5 minutes
```

**Действие:**
- **Critical:** PagerDuty → on-call engineer
- **Slack:** #incidents channel

**Пример:**
```
🚨 ALERT: Error spike in mes-api
- 45 errors in last 5 minutes (threshold: 10)
- Top error: SQLException "Connection timeout"
- Affected orders: ORD-12345, ORD-12346, ...
- View logs: [Kibana link]
```

#### 2. Slow Queries

**Условие:**
```
query_duration_ms > 5000 AND count > 5 in last 10 minutes
```

**Действие:**
- **Slack:** #performance channel
- **Jira ticket:** Auto-create с деталями

**Пример:**
```
⚠️ Slow query alert
- Query: SELECT * FROM orders WHERE ...
- Duration: 7.5s (threshold: 5s)
- Occurrences: 12 in last 10 min
- Service: shop-api
```

#### 3. Orders Stuck

**Условие:**
```
No status change for order_id in last 60 minutes
AND status != "CLOSED"
```

**Действие:**
- **Slack:** #support channel
- **Email:** support manager

**Реализация:**
- Watcher/Alert каждые 15 минут
- Query Elasticsearch за последний час
- Группировка по `order_id`

#### 4. High RabbitMQ Queue Size

**Условие:**
```
rabbitmq.queue_size > 1000
```

**Действие:**
- **Slack:** #devops
- **Auto-scale:** trigger MES API horizontal scaling (если настроено)

#### 5. Failed Login Attempts (Security)

**Условие:**
```
event:login.failed AND count > 100 from same IP in last 5 minutes
```

**Действие:**
- **PagerDuty:** Security team
- **Auto-block:** Add IP to firewall blacklist (через webhook)
