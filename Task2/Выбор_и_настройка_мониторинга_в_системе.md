# Выбор и настройка мониторинга в системе

## Мотивация

### Бизнес-проблемы
Компания «Александрит» теряет заказы и крупные контракты из-за технических проблем:
- Клиенты не получают заказы месяцами при обещанных 3 неделях
- Потеряно несколько крупных B2B контрактов через месяц после запуска API
- Жалобы от операторов на медленную работу MES

### Что даст мониторинг бизнесу

**Финансовый эффект:**
- **Сохранение выручки:** предотвращение потери контрактов (каждый крупный контракт = значительная выручка)
- **Снижение оттока клиентов B2C:** недовольные клиенты уходят к конкурентам
- **Увеличение пропускной способности:** возможность принимать больше заказов без найма персонала

**Операционный эффект:**
- **Быстрое обнаружение проблем:** вместо жалоб клиентов - автоматические алерты (проблемы решаются за минуты, а не дни)
- **Понимание узких мест:** где именно теряются заказы, что тормозит систему
- **Обоснованное масштабирование:** данные для решений о найме и инфраструктуре

**Без мониторинга:**
- Проблемы обнаруживаются через жалобы клиентов (слишком поздно)
- Невозможно определить причину потери заказов
- Нет данных для планирования роста

## Выбор подхода к мониторингу

Используем комбинированный подход в зависимости от типа компонента:

### 1. **RED метод** - для API сервисов (Shop API, CRM API, MES API)
**Rate, Errors, Duration** - фокус на пользовательском опыте

**Почему:** API - это request/response сервисы, где важна скорость ответа и количество ошибок

**Метрики:**
- **Rate:** количество запросов в секунду
- **Errors:** процент ошибочных ответов (HTTP 500, 400)
- **Duration:** время ответа (latency)

### 2. **USE метод** - для инфраструктуры (БД, RabbitMQ, серверы)
**Utilization, Saturation, Errors** - фокус на ресурсах

**Почему:** Базы данных, очереди и серверы - это ресурсы, которые могут быть перегружены

**Метрики:**
- **Utilization:** CPU, Memory, DB connections
- **Saturation:** очередь сообщений RabbitMQ, количество ожидающих подключений
- **Errors:** dead letter queue, failed queries

### 3. **Бизнес-метрики** - сквозные процессы
Дополнительно к RED и USE добавляем метрики бизнес-процессов:
- Количество заказов по статусам
- Время прохождения заказа через все этапы
- Количество "застрявших" заказов (в одном статусе > N часов)

## Метрики для отслеживания

### Критичные метрики (P0) - мониторим обязательно

#### RabbitMQ (USE)

**1. Number of dead-letter-exchange letters in RabbitMQ**
- **Зачем:** Показывает потерянные сообщения = потерянные заказы. Это прямая индикация проблемы.
- **Ярлыки:** `queue_name` (order_created, price_calculated, etc), `exchange`
- **Алерт:** > 0 сообщений в DLQ

**2. Number of messages in flight in RabbitMQ**
- **Зачем:** Показывает накопление необработанных сообщений (saturation). Если растёт - система не справляется.
- **Ярлыки:** `queue_name`, `environment` (prod/release/dev)
- **Алерт:** > 1000 сообщений в очереди

#### API сервисы (RED)

**3. Number of requests (RPS) for shop/CRM/MES API**
- **Зачем:** Rate - базовая метрика нагрузки. Показывает тренды и аномалии (внезапные спайки или падения).
- **Ярлыки:** `service` (shop/crm/mes), `endpoint` (/orders, /calculate-price, etc), `method` (GET/POST)
- **Без алерта, но важно для анализа**

**4. Response time (latency) for shop/CRM/MES API**
- **Зачем:** Duration - пользовательский опыт. Медленные ответы = недовольные клиенты.
- **Ярлыки:** `service`, `endpoint`, `percentile` (p50, p95, p99)
- **Алерт:** p95 > 2 секунды, p99 > 5 секунд

**5. Number of HTTP 500 for shop/CRM/MES API**
- **Зачем:** Errors - прямая индикация проблем. HTTP 500 = сломанная функциональность.
- **Ярлыки:** `service`, `endpoint`, `error_type`
- **Алерт:** Error rate > 1% от общего RPS

**6. Number of HTTP 200 for shop/CRM/MES API**
- **Зачем:** Success rate - базовая метрика здоровья. Используется для расчёта % ошибок.
- **Ярлыки:** `service`, `endpoint`
- **Без алерта**

#### Базы данных (USE)

**7. Number of connections for shop/MES db instance**
- **Зачем:** Utilization + Saturation. Исчерпание пула коннектов = отказ сервиса.
- **Ярлыки:** `database` (shop_db/mes_db), `connection_state` (active/idle)
- **Алерт:** > 80% от max_connections

**8. Memory Utilisation for shop/MES db instance**
- **Зачем:** Utilization. Нехватка памяти = swap = деградация производительности.
- **Ярлыки:** `database`, `memory_type` (buffer_pool/total)
- **Алерт:** > 85%

### Важные метрики (P1) - мониторим для анализа

**9. CPU % for shop/CRM/MES API**
- **Зачем:** Utilization. Показывает нагрузку на инстансы и необходимость масштабирования.
- **Ярлыки:** `service`, `instance_id`
- **Алерт:** > 80% более 5 минут

**10. Memory Utilisation for shop/CRM/MES API**
- **Зачем:** Utilization. Memory leak или недостаток ресурсов.
- **Ярлыки:** `service`, `instance_id`, `memory_type` (heap/non-heap для JVM)
- **Алерт:** > 90%

**11. Number of requests (RPS) per user for shop API (внешний API)**
- **Зачем:** Обнаружение abuse от B2B клиентов. Rate limiting.
- **Ярлыки:** `api_key`, `client_name`
- **Алерт:** > 100 RPS от одного клиента

**12. Size of shop/MES db instance**
- **Зачем:** Планирование роста, предотвращение исчерпания дискового пространства.
- **Ярлыки:** `database`
- **Алерт:** > 80% от выделенного объёма

**13. Size of S3 storage**
- **Зачем:** Контроль стоимости хранения 3D-моделей и планирование бюджета.
- **Ярлыки:** `bucket_name`
- **Алерт:** рост > 50% за месяц (для бюджетного планирования)

### Дополнительные метрики (P2) - Nice to have

**14. Number of simultaneous sessions for CRM/MES API**
- **Зачем:** Понимание реальной нагрузки от операторов и менеджеров.
- **Ярлыки:** `service`
- **Без алерта**

**15. Kb transferred (received/sent) for shop/CRM/MES API**
- **Зачем:** Анализ трафика, обнаружение аномалий (например, большие файлы).
- **Ярлыки:** `service`, `direction` (in/out)
- **Без алерта**

### Дополнительные метрики (не из списка)

**16. Order processing time by status** (НОВАЯ)
- **Зачем:** Бизнес-метрика. Время прохождения заказа через каждый статус. Показывает узкие места.
- **Ярлыки:** `from_status`, `to_status` (SUBMITTED→PRICE_CALCULATED, etc)
- **Алерт:** > 30 минут для расчёта цены, > 24 часа для MANUFACTURING_APPROVED→MANUFACTURING_STARTED

**17. Number of orders stuck in status** (НОВАЯ)
- **Зачем:** Бизнес-метрика. Заказы, которые "застряли" и не переходят дальше.
- **Ярлыки:** `status`
- **Алерт:** > 10 заказов в статусе SUBMITTED более 1 часа

**18. RabbitMQ message processing time** (НОВАЯ)
- **Зачем:** Latency обработки сообщений. Показывает задержки в асинхронной коммуникации.
- **Ярлыки:** `queue_name`, `consumer_service`
- **Алерт:** p95 > 10 секунд

## Метрики, которые НЕ используем (и почему)

❌ **Number of requests (RPS) per user for CRM/MES API**
- **Почему:** Внутренние пользователи (операторы, менеджеры) - небольшое количество, нет риска abuse

❌ **Kb transferred для внутренних API (CRM/MES)**
- **Почему:** Низкий приоритет, трафик внутренний и не критичен

- HTTP метрики (RPS, latency, errors) - автоматически через Spring Actuator
- Бизнес-метрики: order processing time, orders by status
- DB connection pool metrics

**2.3. Реализовать метрики в CRM API (Java)**

**2.4. Реализовать метрики в MES API (C#)**
- HTTP метрики через prometheus-net middleware
- Бизнес-метрики: operator dashboard load time

**2.5. Настроить Node exporter на всех EC2**
- CPU, Memory, Disk metrics для инстансов

**2.6. Подключить Yandex Cloud Monitoring для БД**
- Автоматические метрики для Managed PostgreSQL/MySQL

### Этап 3: Дашборды и алерты (1 неделя)

**3.1. Создать дашборды в Grafana**
- **Overview Dashboard:** общее состояние системы (RPS, errors, latency всех сервисов)
- **Orders Dashboard:** бизнес-метрики заказов (по статусам, stuck orders, processing time)
- **RabbitMQ Dashboard:** очереди, DLQ, message rate
- **Infrastructure Dashboard:** CPU, Memory, DB connections
- **Per-Service Dashboards:** детальные метрики для каждого сервиса

**3.2. Настроить алерты (критичные)**
- DLQ messages > 0
- Error rate > 1%
- Response latency p99 > 5s
- DB connections > 80%
- Orders stuck > 10 in any status > 1h
- RabbitMQ queue size > 1000

**3.3. Настроить алерты (некритичные - warning)**
- CPU > 80% for 5 min
- Memory > 90%
- DB size > 80%

## Дополнительное задание: Показатели насыщенности (Saturation)

### Определение порогов насыщенности

| Метрика | Порог Warning | Порог Critical | Обоснование |
|---------|---------------|----------------|-------------|
| **RabbitMQ queue size** | 500 msgs | 1000 msgs | При 1000+ сообщений система не успевает обрабатывать, заказы "стареют" |
| **DB connections** | 70% | 85% | При 85% начинаются отказы в соединении, 70% - запас для спайков |
| **CPU %** | 75% | 90% | При 90% API начинает тормозить, 75% - время для масштабирования |
| **Memory %** | 80% | 95% | При 95% риск OOM, 80% - начало swap и деградации |
| **DB size** | 75% | 90% | При 90% критично мало места, 75% - время для расширения диска |
| **S3 storage** | - | 1 TB (бюджет) | Контроль стоимости |

### Действия при превышении порогов

#### Warning уровень (автоматические действия)

**RabbitMQ queue size > 500:**
1. Алерт в Slack #engineering
2. Создать Jira ticket с priority=High
3. Действие: команда анализирует, почему consumer не успевает

**DB connections > 70%:**
1. Алерт в Slack
2. Действие:
   - Проверить долгие запросы (pg_stat_activity)
   - Оценить необходимость read replica

**CPU > 75% for 10 min:**
1. Алерт в Slack
2. Создать Jira ticket
3. Действие: планирование добавления инстанса (не срочно)

**Memory > 80%:**
1. Алерт в Slack
2. Действие: анализ memory leak, планирование увеличения RAM

**DB size > 75%:**
1. Алерт в Slack
2. Создать Jira ticket
3. Действие: планирование расширения диска (выполнить в течение недели)

#### Critical уровень (немедленные действия)

**RabbitMQ queue size > 1000:**
1. **Алерт:** PagerDuty call to on-call engineer
2. **Немедленное действие:**
   - Анализ через Grafana: какая очередь переполнена
   - Проверка логов consumer'а
   - Временное решение: рестарт consumer или добавление инстанса вручную
3. **Постоянное решение:** масштабирование consumer'ов

**DB connections > 85%:**
1. **Алерт:** PagerDuty call
2. **Немедленное действие:**
   - Kill idle connections: `SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE state = 'idle' AND query_start < now() - interval '10 minutes'`
   - Проверить connection leak в приложении
3. **Постоянное решение:** увеличение max_connections или connection pooling

**CPU > 90% for 5 min:**
1. **Алерт:** PagerDuty call
2. **Немедленное действие:**
   - Поднять дополнительный инстанс вручную
   - Проверить аномальную нагрузку (DDoS? bug?)
3. **Постоянное решение:** horizontal pod autoscaling

**Memory > 95%:**
1. **Алерт:** PagerDuty call
2. **Немедленное действие:**
   - Рестарт приложения на новом инстансе (graceful)
   - Анализ heap dump (для JVM)
3. **Постоянное решение:** исправление memory leak

**DB size > 90%:**
1. **Алерт:** PagerDuty call + email to DevOps lead
2. **Немедленное действие:**
   - Расширение диска через Yandex Cloud (в течение 1 часа)
   - Очистка старых данных если возможно
3. **Постоянное решение:** архивирование старых заказов

**S3 storage > budget limit:**
1. **Алерт:** Email to product manager + CFO
2. **Действие:**
   - Анализ роста (легитимный или bug?)
   - Переход на Glacier для старых 3D-моделей (>6 месяцев)
   - Согласование дополнительного бюджета

### Автоматизация реакции (roadmap)

**Краткосрочно (сейчас):**
- Алерты + manual intervention

**Среднесрочно (через 3 месяца):**
- Auto-scaling для API сервисов при CPU > 75%
- Автоматическое расширение DB дисков при достижении 85%

**Долгосрочно (через 6 месяцев):**
- Predictive scaling на основе ML (рост нагрузки +100 заказов/месяц предсказуем)
- Self-healing для consumer'ов (автоматический рестарт при накоплении очереди)
