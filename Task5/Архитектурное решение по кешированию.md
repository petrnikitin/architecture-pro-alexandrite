# Архитектурное решение по кешированию

## Мотивация

### Проблемы

**1. Медленная загрузка дашборда MES**
- Операторы ждут 30+ секунд загрузки списка заказов
- Каждое обновление = новый запрос к БД

**2. Повторяющиеся запросы к каталогу**
- Список товаров меняется редко
- Каждый клиент запрашивает каталог
- БД под нагрузкой

### Что даст кеширование

- Загрузка дашборда: 30с → 1-2с (15x)
- Снижение нагрузки на БД: -70%
- Операторы могут быстрее обрабатывать заказы

---

## Элементы системы для кеширования

### Приоритет 1 (критично)

**1. MES Dashboard - список заказов**
- **Что кешируем:** Результат запроса "список заказов по статусам + фильтры"
- **TTL:** 30 секунд
- **Cache key:** `mes_dashboard:{status}:{page}`
- **Объём:** ~10-50 MB

**2. Shop API - каталог товаров**
- **Что кешируем:** Список изделий
- **TTL:** 1 час
- **Cache key:** `shop_catalog:all`
- **Объём:** ~5 MB

### Приоритет 2 (полезно)

**3. CRM - данные пользователей**
- User profile, permissions
- TTL: 15 минут

## Предлагаемое решение

### Технология: Redis

**Почему Redis:**
- In-memory storage (быстро)
- TTL из коробки
- Кластеризация для HA

**Deployment:**
- Managed Redis в Yandex Cloud
- Cost: ~$150/месяц

---

### Решение 1: MES Dashboard

**Паттерн:** Cache-Aside
**TTL:** 30 секунд
**Логика:** Проверить Redis → Cache HIT: вернуть данные → Cache MISS: запросить БД, сохранить в Redis

#### Sequence диаграмма 1: Чтение списка заказов

**Сценарий:** Оператор открывает дашборд MES

**Диаграмма:** [sequence_read_orders.puml](./sequence_read_orders.puml)

**Ключевые моменты:**
- Cache HIT: возврат данных за ~5ms
- Cache MISS: запрос к БД за ~2000ms, затем сохранение в Redis с TTL 30 сек
- Паттерн Cache-Aside: приложение управляет кешем

#### Sequence диаграмма 2: Изменение статуса заказа

**Сценарий:** Менеджер подтверждает заказ

**Диаграмма:** [sequence_update_order_status.puml](./sequence_update_order_status.puml)

**Ключевые моменты:**
- UPDATE в БД → DEL в Redis (инвалидация кеша)
- Удаляем кеш для обоих затронутых статусов (SUBMITTED и APPROVED)
- Pub/Sub в RabbitMQ для уведомления других сервисов
- Следующий GET запрос заполнит кеш заново

---

### Решение 2: Каталог товаров

**Паттерн:** Cache-Aside + HTTP Cache
**TTL:** 1 час (серверный), ETag для клиентов
**Логика:** Redis для серверного кеша + HTTP Cache-Control для браузеров

#### Sequence диаграмма 3: Чтение каталога товаров

**Сценарий:** Клиент открывает интернет-магазин

**Диаграмма:** [sequence_read_catalog.puml](./sequence_read_catalog.puml)

**Ключевые моменты:**
- Двухуровневое кеширование: браузер (HTTP Cache) + сервер (Redis)
- HTTP 304 Not Modified при совпадении ETag
- Cache-Control: max-age=3600 для браузера
- Redis TTL: 1 час

## Сравнение стратегий инвалидации кеша

| Стратегия | Преимущества | Недостатки | Подходит для |
|-----------|--------------|------------|--------------|
| **TTL** | Простота, автоматическая очистка | Stale data до истечения TTL | MES Dashboard (30s) |
| **Инвалидация по ключу** | Актуальные данные | Сложная логика, race conditions | Критичные изменения |
| **Write-Through** | Всегда актуальный кеш | Overhead на запись | ❌ Не подходит для read-heavy |
| **Pub/Sub** | Синхронизация между инстансами | Нужна инфраструктура | Дополнение к TTL |

**Рекомендация:** TTL как основа + Pub/Sub для критичных случаев
