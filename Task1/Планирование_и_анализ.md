# Задание 1. Анализ, идентификация проблем и решений, планирование

## 1. Проблемные места

### Критические проблемы (влияют на бизнес сейчас)
1. **Потеря заказов** - клиенты не получают заказы, контракты потеряны
2. **Отсутствие observability** - нет понимания, где теряются заказы
3. **Single Point of Failure** - по одному инстансу каждого сервиса
4. **Ненадёжная доставка сообщений RabbitMQ** - нет гарантий обработки
5. **Медленный дашборд MES** - операторы не могут быстро взять заказы в работу

### Высокий риск (проблемы в ближайшем будущем)
6. **Отсутствие горизонтального масштабирования** - нагрузка растёт +100 заказов/мес
7. **База данных на чтение и запись - один инстанс** - узкое горло производительности
8. **Долгий расчёт стоимости (2-30 мин)** - блокирует создание заказа
9. **Медленные релизы** - ручное E2E тестирование, задержки до месяца

### Средний риск
10. **Нет кеширования** - каждый запрос к БД
11. **Нет rate limiting для API** - внешние клиенты могут перегрузить систему
12. **Shared database между системами** - Shop DB и CRM DB используются разными сервисами

---

## 2. Инициативы для устранения проблем

### Мониторинг и observability
**I1.** Внедрить distributed tracing (Jaeger/Tempo) для отслеживания заказов через все системы

**I2.** Добавить метрики и алерты (Prometheus + Grafana):
- Количество сообщений в очередях RabbitMQ
- Задержки обработки заказов
- Ошибки интеграций между системами

**I3.** Централизованное логирование (ELK/Loki) для поиска потерянных заказов

### Надёжность доставки сообщений
**I4.** Реализовать pattern "Outbox" для гарантированной доставки сообщений:
- Сохранение событий в БД в транзакции с бизнес-данными
- Отдельный процесс отправки в RabbitMQ с retry

**I5.** Добавить Dead Letter Queue (DLQ) в RabbitMQ для анализа не обработанных сообщений

**I6.** Реализовать idempotency для обработки сообщений (защита от дублей)

### Масштабирование и производительность
**I7.** Горизонтальное масштабирование:
- Shop API: 2-3 инстанса + Load Balancer
- CRM API: 2-3 инстанса + Load Balancer
- MES API: 2-3 инстанса + Load Balancer

**I8.** Read Replica для баз данных:
- Shop DB: master + 1-2 read replicas
- MES DB: master + 1-2 read replicas

**I9.** Оптимизация дашборда MES:
- Материализованные представления для статистики
- Индексы на поля фильтрации (статус, дата создания)
- Кеширование списка заказов (Redis) с TTL 30-60 сек

**I10.** Асинхронный расчёт стоимости:
- Не блокировать создание заказа
- Статус PRICE_CALCULATING → webhook/polling для получения результата

### Автоматизация и процессы
**I11.** Автоматизация E2E тестов:
- Критичные сценарии: создание заказа end-to-end
- Интеграция в CI/CD

**I12.** Автоматический деплой в release после прохождения автотестов

### Архитектурные улучшения
**I13.** Rate limiting для внешнего API (защита от перегрузки)

**I14.** Разделение БД: каждый сервис - своя БД (постепенная миграция)

**I15.** Кеширование (Redis):
- Каталог товаров (Shop)
- Данные пользователей (CRM)

## 4. Целевая архитектура через полгода

### Ключевые изменения:

**Observability:**
- Distributed tracing во всех сервисах
- Метрики, дашборды, алерты
- Централизованные логи

**Надёжность:**
- Outbox pattern для всех интеграций через RabbitMQ
- DLQ и idempotency
- 2-3 инстанса каждого сервиса за Load Balancer
- Read replicas для БД

**Производительность:**
- Оптимизированный дашборд MES (материализованные view + индексы + кеш)
- Кеширование часто запрашиваемых данных (Redis)

**Процессы:**
- Автоматизированные E2E тесты для критичных сценариев
- Релизы 2 раза в месяц вместо задержек

**Результат:**
- **0 потерянных заказов** - благодаря tracing и надёжной доставке сообщений
- **RTO < 5 мин** - несколько инстансов, быстрое переключение
- **Пропускная способность x3** - готовность к росту нагрузки
- **Время релиза: 1-2 дня** вместо недель/месяцев

## 5. Топ-3 инициативы на ближайшие полгода

Если можно выполнить только 3 пункта:

### 1. **I4 - Outbox pattern** (2 месяца, 1 Java dev + 1 C# dev)
**Почему первое:**
- Решает корневую причину потери заказов
- Гарантирует доставку всех сообщений между системами
- Без этого все остальные улучшения бесполезны

**Реализация:**
- Таблица outbox_events в Shop DB, CRM DB, MES DB
- Background job для отправки событий в RabbitMQ с retry
- Очистка старых записей (> 7 дней)

### 2. **I1 - Distributed tracing** (1 месяц, 1 Java dev + 1 C# dev + DevOps)
**Почему второе:**
- Даёт видимость: где заказ застрял, какие этапы пройдены
- Позволяет быстро находить проблемы в продакшене
- Необходимо для мониторинга эффекта от Outbox pattern

**Реализация:**
- Jaeger/Tempo в Yandex Cloud
- OpenTelemetry SDK во всех сервисах
- Trace ID в логах и RabbitMQ headers

### 3. **I7 - Горизонтальное масштабирование** (1.5 месяца, DevOps + тестирование)
**Почему третье:**
- Устраняет Single Point of Failure - критично для бизнеса
- Позволяет справиться с ростом нагрузки (+100 заказов/мес)
- Относительно быстрая реализация (Yandex Cloud Load Balancer + автоскейлинг)

**Реализация:**
- Application Load Balancer для Shop API, CRM API, MES API
- 2 инстанса каждого сервиса (можно начать с минимума)
- Health checks и graceful shutdown
- Sticky sessions для CRM/MES (если используется in-memory session)

## Обоснование выбора

**Не включены в топ-3, но важны:**
- **I9 (Оптимизация дашборда MES)** - можно сделать быстро (2 недели), но это симптом, а не причина. После I7 (масштабирование) + I8 (read replicas) проблема может уйти сама.
- **I2 (Метрики и алерты)** - важно, но можно начать после I1 (tracing уже даст базовую видимость).

**Риски:**
- Если не сделать I4 (Outbox) - заказы продолжат теряться, клиенты уходят
- Если не сделать I1 (Tracing) - не сможем доказать, что проблема решена
- Если не сделать I7 (Масштабирование) - любой сбой одного инстанса = простой системы

**Итого:** За 4.5 месяца команда получит надёжную систему с observability и готовностью к росту. Оставшиеся 1.5 месяца - на I9 (MES дашборд) и I5+I6 (DLQ + idempotency).
